## Goal

Add first-class **quest templates** — authored, reusable quest definitions
that can be instantiated into concrete `Quest` aggregates (S28). S28 built
the quest *instance* layer (domain aggregate + lifecycle + persistence +
commit integration); this sprint adds the design-time definition layer that
produces those instances. A template declares a stable key, display content,
and an ordered set of objective definitions; instantiating it creates a
`Quest` pre-populated with that structure, then follows the normal S28
lifecycle (`inactive → active → …`).

This is purely additive: no existing quest behavior changes, and the S28
schema is extended (not rewritten) so instances remain untouched.

## Principle

- A **template is a definition**, a **quest is an instance**. Templates are
  versioned, keyed, and household-or-world agnostic at definition time; a
  concrete quest binds them to a household/world/session.
- Templates are **authored** (design-time data), not generated by LLM at
  runtime. No prompt or LLM output produces a template.
- Instantiating a template is **deterministic** and **additive**: it only
  writes a new `Quest` row plus its objective rows; it never mutates an
  existing quest.
- Template -> instance mapping is 1:N (a template may seed many quests
  across worlds) but each template is **idempotency-friendly** via an
  optional caller-provided key (tooling can dedupe re-instantiation).
- Objective definitions carry a **stable key** and **title** only — no
  status logic. Status/lifecycle remains owned by the `Quest` aggregate
  (S28) so definition ≠ runtime state.

## In Scope

- **QuestTemplate domain model**: `QuestTemplate` aggregate with stable
  `templateKey`, display metadata, and ordered `QuestTemplateObjective`
  definitions (each a stable key + title).
- **Template persistence**: `quest_templates` + `quest_template_objectives`
  tables (definition-time, not household-scoped; unique `template_key`),
  forward-only migration `0007_quest_templates.sql`.
- **Template application service**: `QuestTemplateService` —
  `createTemplate` / `getTemplateByKey` / `listTemplates` /
  `instantiateTemplate` (rolls a template into a `Quest` via S28).
- **Template repo port + Drizzle impl**: `QuestTemplateRepository` +
  `DrizzleQuestTemplateRepository` (CREATE/READ only — templates are
  authored, not updated/deleted in scope).
- **Instantiation**: `instantiateTemplate(templateKey, { householdId,
  worldId, storySessionId? })` maps template objectives -> quest
  objectives and persists through the existing `QuestService`.
- **Backlog validation evidence**: map S28/backlog quest-template
  requirement to covered coverage + exit criteria P0/P1 green.

## Out of Scope

- UI / authoring tooling for templates (seed via code/migration is
  accepted; no web route in this sprint).
- Household-scoped or user-editable templates (definition-time only;
  edition = additive new version, deferred).
- Objective auto-unlocking / prerequisite logic (definition-only).
- Template reward / inventory grants (reuse existing
  `inventory_transaction` outcome when rewards land).
- `quest_seed` interaction -> template -> quest automation (separate
  backlog step; this sprint exposes instantiation primitives only).
- Template versioning/deprecation lifecycle (future).

## Requirements

- A template has a stable `templateKey` (unique), a display name, a short
  description, and 1..N ordered objective definitions (each with a stable
  objective key + title); N >= 1 is enforced.
- Duplicate `templateKey` is rejected (uniqueness at domain + DB index).
- Templates are additive-only: created and read; no in-place update or
  delete in this sprint.
- `instantiateTemplate` produces a `Quest` via `Quest.create` with the
  same ordered objective titles, in `inactive` status, bound to the given
  householdId / worldId / optional storySessionId.
- Instantiation writes the quest and its objectives in a transaction and
  returns the persisted `QuestState`.
- Definition data never mutates `Quest` status/versioning logic; all
  runtime semantics stay in the S28 aggregate.

## Acceptance Criteria

- [ ] Creating a template persists it with a unique `templateKey` and
  ordered objective definitions.
- [ ] A duplicate `templateKey` creation is rejected (domain + DB guard).
- [ ] A template with zero objectives is rejected.
- [ ] Listing/getting templates returns authored definitions.
- [ ] Instantiating a template creates one `Quest` in `inactive` status
  with matching ordered objectives.
- [ ] Instantiation persists through the existing `QuestRepository`; no
  status lifecycle logic lives in the template layer.
- [ ] All source green: `format:check | lint | typecheck | test | build`.

## Risks

- Scope creep into a web/editor surface: keep templates = code/migration
  data this sprint; no routes/UI.
- Over-coupling template => instance: instantiation is the *only* bridge;
  templates must not drive provider `quest` writes directly.
- Migration ordering: `0007` references only tables from earlier
  migrations; verify it applies cleanly on top of `0006`.
- Household/world agnosticism at definition time vs. instance binding:
  keep template rows definition-time, bind only at instantiate.
